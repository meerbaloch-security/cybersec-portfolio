# Project 01: Enterprise Active Directory Detection Lab

> **Status:** Active Directory foundation completed — telemetry and Splunk detection engineering in progress

## Overview

This project documents the development of an isolated enterprise-style Active Directory security lab.

The environment is designed to support authorized security testing from Kali Linux, Windows authentication auditing, centralized log collection, incident investigation, and the development of practical Splunk detections.

The first phase of the project established and validated the core Active Directory environment. Future phases will add Sysmon, centralized telemetry, controlled attack simulations, and Splunk detection rules.

> All security testing is performed only against systems created and owned by the project author in an isolated VirtualBox lab.

## Objectives

* Build an isolated Windows domain environment.
* Deploy Active Directory Domain Services and DNS.
* Organize domain users and computers.
* Join a Windows workstation to the domain.
* Validate domain-user authentication.
* Configure and test password and account-lockout controls.
* Analyze Windows Security events generated by authentication activity.
* Perform authorized network reconnaissance from Kali Linux.
* Validate important security controls such as SMB signing.
* Centralize Windows telemetry in Splunk.
* Develop and test practical security detections.

## Password and Account-Lockout Policy

The Active Directory password policy was inspected using:

```powershell
Get-ADDefaultDomainPasswordPolicy |
Format-List MinPasswordLength,PasswordHistoryCount,ComplexityEnabled,MaxPasswordAge,LockoutThreshold,LockoutDuration,LockoutObservationWindow
```

The tested account-lockout settings included:

| Control                  | Configured value                 |
| ------------------------ | -------------------------------- |
| Lockout threshold        | 5 failed authentication attempts |
| Lockout duration         | 15 minutes                       |
| Observation/reset window | 15 minutes                       |
| Password complexity      | Enabled                          |

These controls help limit repeated password-guessing attempts against domain accounts.

![Password and account-lockout policy](evidence/02-password-lockout-policy.png)

## Account-Lockout Investigation

Controlled incorrect authentication attempts were performed against the test account from `WS01`.

After the configured threshold was reached, Windows Security Event ID `4740` was generated on the domain controller.

The event identified:

* Locked account: `ajohnson`
* Caller computer: `WS01`
* Event source: Microsoft Windows security auditing

This confirmed that the lockout policy functioned correctly and that the originating workstation was recorded.

![Windows Security Event 4740](evidence/07-account-lockout-4740.png)

After the investigation, the account was restored using:

```powershell
Unlock-ADAccount -Identity ajohnson
```

Successful access with the correct password was then confirmed.

> Event ID `4740` is the primary captured evidence for this test. A separate Event ID `4625` screenshot is not currently included.

## Authorized Network Reconnaissance

An authorized Nmap service and version scan was performed against `DC01`:

```bash
sudo nmap -sV 192.168.56.5
```

The scan identified services expected on an Active Directory domain controller:

| Port | Service                   | Purpose                             |
| ---: | ------------------------- | ----------------------------------- |
|   53 | DNS                       | Domain name resolution              |
|   88 | Kerberos                  | Domain authentication               |
|  135 | Microsoft RPC             | Windows remote procedure calls      |
|  139 | NetBIOS                   | Legacy Windows networking           |
|  389 | LDAP                      | Active Directory directory access   |
|  445 | SMB                       | Windows file and directory services |
|  464 | Kerberos password service | Password operations                 |
|  593 | RPC over HTTP             | RPC transport                       |
| 3268 | Global Catalog LDAP       | Forest-wide directory queries       |

The exposed services were consistent with the intended role of `DC01`.

![Nmap service scan against DC01](evidence/09-dc01-nmap-services.png)

## SMB Signing Validation

SMB security settings were evaluated using authorized Nmap scripts:

```bash
sudo nmap -p 445 --script smb2-security-mode,smb2-time 192.168.56.5
```

The scan reported:

```text
Message signing enabled and required
```

Requiring SMB message signing helps protect SMB traffic against tampering and certain man-in-the-middle attacks.

![SMB signing validation](evidence/10-smb-signing.png)

## Lab Limitation

VirtualBox time synchronization caused inconsistent timestamps between some virtual machines during testing. This affected displayed timestamps in some Windows and Nmap results but did not prevent domain authentication, lockout validation, event collection, network scanning, or SMB security verification.

In a production environment, the domain controller should synchronize with a reliable time source, while domain members should follow the Active Directory time hierarchy. Accurate time is essential for Kerberos authentication and reliable event correlation.
